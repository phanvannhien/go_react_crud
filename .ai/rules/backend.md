# Backend Rules (Enterprise Edition)

Purpose:
Define strict backend implementation constraints to ensure
architecture consistency, security, performance, and maintainability.

---

# STACK

- Go 1.24
- Echo
- PostgreSQL (pgx)
- sqlc
- dbmate

---

# ARCHITECTURE

Clean architecture mandatory.

Layers:

- handler
- service
- repository (generated by sqlc)
- domain (optional if business complexity requires)

Flow:

Handler → Service → sqlc Repository

Strict prohibitions:

- No DB calls in handler
- No business logic in handler
- No SQL outside /db/query
- No raw SQL string concatenation
- No circular dependency

---

# DIRECTORY RULES

- All SQL: `/db/query`
- All migrations: `/db/migrations`
- Services: `/internal/service`
- Handlers: `/internal/handler`
- Routes: `/internal/routes`
- Tests: `/internal/test`

---

# DEPENDENCY RULES

- No global variables
- No singleton DB access
- All dependencies injected via constructor
- All handlers and services accept `context.Context`
- DB access only through sqlc Queries struct

---

# ERROR HANDLING

- All errors wrapped using:
  fmt.Errorf("context: %w", err)
- No leaking internal DB errors directly to client
- Map internal errors → structured API error

Response format:

{
  "data": ...,
  "error": null
}

Validation error:

{
  "error": "validation_error",
  "details": {...}
}

Internal error:

{
  "error": "internal_error"
}

---

# VALIDATION RULES

Validation must happen in handler layer using DTO structs.

Mandatory:

- UUID format validation
- Required fields non-empty
- Email format validation
- Numeric range validation
- Boolean strict parsing
- Timestamp RFC3339 only

Service layer must not blindly trust handler.

No inline ad-hoc validation inside business logic.

---

# LIST ENDPOINT REQUIREMENTS

Every list endpoint MUST support:

Query params:

- page
- limit
- sort
- order
- filters

Rules:

- Enforce max limit cap (e.g., 100)
- Always require LIMIT
- Always require ORDER BY (whitelisted)
- Must return total count
- Must never allow dynamic SQL building
- Must whitelist sortable fields
- Must whitelist filterable fields

Offset calculation:

offset = (page - 1) * limit

---

# CURSOR PAGINATION (High Scale Tables)

If table expected to grow large:

- Prefer cursor pagination
- Cursor field must be indexed
- Cursor must be stable (UUID or created_at)
- No OFFSET in high-scale mode

Cursor response format:

{
  "data": [],
  "next_cursor": "value"
}

---

# FILTER STRATEGY (sqlc-safe)

Filters must use typed parameters:

Example pattern:

WHERE
  ($1::text IS NULL OR email ILIKE '%' || $1 || '%')
  AND ($2::uuid IS NULL OR role_id = $2)

Rules:

- No dynamic WHERE string building
- No string concatenation
- All filter fields must be explicitly typed
- Only filterable fields allowed

---

# QUERY RULES

Prohibited:

- SELECT *
- Unbounded query
- Missing LIMIT
- ORDER BY user input without whitelist
- Dynamic table names

Mandatory:

- Explicit column selection
- Indexed ORDER BY column
- Parameterized SQL only
- COUNT query for pagination

---

# PERFORMANCE RULES

- Index all:
  - Foreign keys
  - Unique fields
  - Searchable fields
  - Sortable fields
- Suggest composite index if multiple filters common
- Avoid OFFSET for large dataset
- Avoid N+1 query pattern
- Batch operations must use transaction

---

# TRANSACTION RULES

Use transaction when:

- Multiple writes in one operation
- Cross-table consistency required
- Business invariants enforced

Transaction must:

- Accept context
- Rollback on error
- Commit only if no error

No nested transaction unless required.

---

# SECURITY RULES

Mandatory:

- Auth middleware if endpoint protected
- Validate all query params
- No mass assignment
- No returning sensitive fields (password_hash)
- No exposing internal IDs if unnecessary
- No panic propagation to client

---

# OBSERVABILITY

- Use structured logging
- Log request ID if available
- Log errors with context
- No logging sensitive data

---

# TESTING REQUIREMENTS

Every module must have:

- Integration test
- Filter test
- Pagination test
- Validation test
- Error scenario test

Integration test must:

- Spin test DB
- Insert fixture
- Call handler
- Validate JSON response

---

# FAILURE CONDITIONS

Reject implementation if:

- Handler calls DB
- SQL outside /db/query
- SELECT *
- Missing LIMIT
- Missing validation
- Missing error wrapping
- Dynamic SQL string building
- Missing max limit cap
- No total count in list endpoint
- No ORDER BY whitelist
- Missing context.Context

---

# HIGH SCALE MODE (Optional)

If enabled:

- Force cursor pagination
- Force composite indexes
- Force created_at index
- Prohibit OFFSET usage
- Recommend read replica
- Recommend soft delete

---

# FINAL OBJECTIVE

Backend must be:

- Clean-architecture compliant
- Deterministic
- Secure
- Scalable
- Index-aware
- Fully validated
- Test-covered
- SQL injection safe
